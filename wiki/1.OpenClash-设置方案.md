## ✨ 本方案所实现的效果

严格按照本方案配置 OpenClash，无需叠加其他工具（如 MosDNS）即可实现以下功能：

- 🚀 **优化 DNS 与直连路径**
    常见直连域名使用本地解析；同时命中 GeoSite 的 `cn` 分类和中国大陆 IP 地址段的流量不进入内核，从而降低性能损耗。

- 🛡️ **降低解析异常与泄漏风险**
    对需要经内核 Proxy 处理的域名，解析请求交由远端处理，以获得更一致的解析结果。

- 🧩 **减少多插件叠加**
    尽量使用 OpenClash 完成分流与解析逻辑，避免多插件叠加带来的不确定性。

- 🖱️ **可复刻的设置流程**
    按图操作即可完成一套可长期使用的完整设置，无需从零手动编写配置。

- 🔀 **覆盖常见场景的策略组**
    包含常见应用和平台的策略组，并提供轻量版供按需选择。

- ⚡ **支持策略组自动优选（可选）**
    可以根据延迟和可用性自动选择更合适的出站项，减少手动切换。

- 🎮 **Steam 访问优化**
    单独列出 Steam 规则并强制 Steam 下载 CDN 走直连，避免下载流量进入内核。

- 🤖 **自动更新，长期无人值守**
    设置完成后可定时更新上游规则、GeoIP、GeoSite 与直连白名单等数据。

- 📥 **大流量下载优化（尝试）**
    尽量避免下载流量进入内核，降低不必要的消耗。

- 🚫 **支持广告过滤与 hosts 加速（可选）**
    可配合系统自带的 dnsmasq 实现基础广告过滤与 `hosts` 加速，并支持自动更新。

- 🕸️ **补充若干小众域名规则**
    可通过 PR 提交域名参与完善规则。

### 0.2 关于旁路由

> [!WARNING]
> 「旁路由」是一种**错误**的组网方法，**反对**部署所谓的「旁路由」，**强烈建议**使用 OpenWrt 作为唯一主路由。

维护者始终认为，在单一主路由可以满足需求时，使用旁路由只会人为增加网络复杂度和故障点。

> 个人观点：[关于「旁路由」的一些吐槽](6.关于“旁路由”的一些吐槽.md)

因此，下文以主路由环境为基础，同时说明涉及旁路由的设置差异。旁路由用户需要根据实际环境调整对应设置；未特别说明的部分无需修改。

**根据维护者处理 GitHub Issue 的经验，其中多数问题与旁路由有关，这也印证了上述观点。**

项目维护者部署的所有设备均采用主路由，以尽量简化网络环境。因此，旁路由设置问题通常不予解答；如根据经验提供建议，也无法保证结果。

### 0.3 关于 IPv6

如果本地网络具备 IPv6，且出站配置支持 IPv6 出站，可以配合本项目的另一套方案实现 OpenClash 与 IPv6 兼容：

🔗 [OpenWrt IPv6 设置方案](https://github.com/Aethersailor/Custom_OpenClash_Rules/wiki/OpenWrt-IPv6-设置方案)

如果不确定出站配置是否支持 IPv6 出站，可以先按方案开启并测试；如测试不通过，再关闭 OpenClash 的 IPv6 相关选项即可。

### 0.4 关于 DNS

> [!IMPORTANT]
> ~~**强烈建议使用运营商通告的 DNS 进行直连域名的解析**，不论是解析速度还是结果的科学性，都不是第三方 DNS 可以比拟的。~~
>
> 鉴于 2025 年以来部分网络环境的变化，运营商 DNS 在某些情况下不一定是最稳定的选择。如遇异常，推荐使用 AliDNS 等加密 DNS，并按需启用 DoH3。
>
> **请结合所在地的网络环境判断以下内容。如遇 DNS 解析问题，建议选择可用的加密 DNS。**

多数情况下，运营商 DNS 对直连类域名的延迟和 CDN 命中更接近实际链路；一般不需要额外用第三方 DNS 做「优选」。

不同递归 DNS 在不同网络环境下，可能出现解析结果不一致或可用性不稳定的情况；如果选择第三方 DNS，优先使用加密协议（DoH 或 DoT）并观察实际效果。

> 以上结论仅来自项目维护者的实际使用经验。MosDNS 和 SmartDNS 本身都是优秀的 DNS 工具。

根据维护者过去在当地网络环境中的长期测试，三大运营商 DNS 通常能为直连域名返回较近的 CDN，和 DNS 插件优选的解析结果基本一致。该经验不代表所有地区与所有时间段；如遇异常，请按上文建议改用可用的加密 DNS。

以维护者所在城市为例，电信和联通线路的 DNS 延迟都很低：高峰时段约为 1～2 毫秒，白天可稳定在 1 毫秒左右。此时使用 DNS 插件很可能产生负优化。

维护者与运营商 DNS 位于同一城市，因此延迟表现较好。如果用户与运营商 DNS 不在同一城市，延迟可能更高，但通常仍优于第三方 DNS。

以下数据来自某三线城市用户长期部署的 SmartDNS，可以对比运营商 DNS 与第三方 DNS 的延迟：

![SmartDNS 延迟对比](https://github.com/user-attachments/assets/7181ec0c-a861-4e72-bfef-7c474c6b9ec4)

按照本方案设置后，运营商 DNS 主要用于解析直连类域名，一般不需要担心解析一致性问题。非直连域名的解析请求交由远端处理，可获得更一致的解析结果，并降低 DNS 泄漏风险。

> [!NOTE]
> 如需使用第三方 DNS，建议优先使用 DoH、DoT、DoH3 或 DoQ 等加密协议。请勿随意使用明文 UDP 公共 DNS，以免出现劫持或解析结果不一致。

### 0.5 关于「套娃」设置

MosDNS、SmartDNS 和 AdGuard Home 本身都是优秀的 DNS 工具，但多个插件叠加并不一定能改善效果，错误的组合反而可能产生负面影响。

**先说结论：在本方案的 Fake-IP 使用场景中，`nameserver` 使用运营商 DNS 或可用的 DoH 服务器，同时不设置 `fallback` 服务器，是维护者推荐的默认设置。** 这种设置兼顾性能开销与解析结果，一般不需要额外调整；如实际网络环境存在异常，再按需修改。

对于非直连域名，通常更适合将解析请求交给远端处理，这样更容易获得与出站链路一致的 CDN 命中。

从延迟和性能开销来看，以维护者所在的网络环境为例：部署本方案后，使用脚本对常见域名进行 30,000 次解析测试，dnsmasq 的解析延迟稳定在 1 ms 左右。加入 AdGuard Home 并启用缓存后，解析时间与 dnsmasq 几乎没有差异，却需要处理缓存与 Fake-IP 并存产生的问题，同时还会影响 Clash 向客户端传递的 TTL 值。

加载大量广告过滤规则后，AdGuard Home 的解析开销甚至略高于 dnsmasq。该结果与维护者及许多用户原先认为 AdGuard Home 在大量规则环境下更具性能优势的预期不同。

部分教程建议新手叠加 AdGuard Home 等插件，并添加多个没有必要的第三方 DNS，最终可能使内网解析延迟达到 5 ms、10 ms 或更高，却将其称为「优化」。相比之下，部分入门级硬路由通过 DHCP 直接分配运营商 DNS，网页访问反而可能更快。

此外，请勿过度依赖乐观缓存。Fake-IP 模式下叠加其他前置缓存插件可能引入更多问题；路由器上的缓存效果也未必优于浏览器和操作系统自带的 DNS 缓存。

> [!WARNING]
> **如果认为 1 ms 的解析时间差异会明显影响使用体验，需要同时评估多插件叠加带来的其他副作用。**

<!-- -->

> [!WARNING]
> **什么情况下有套娃的意义**
>
> 1. 网络支持双栈，并且对中国大陆网站同一域名的 IPv4 和 IPv6 地址的访问性能存在巨大差距。此时可在「NameServer」上游设置 SmartDNS 进行双栈优选。
> 2. 确实需要监控和控制局域网设备的 DNS 请求，例如限制未成年人访问特定网站。此时适合在下游部署 AdGuard Home。
> 除上述两种情况外，其他场景一概没有必要叠加 DNS 插件。

**除非使用存在流量穿透的宽带线路，例如长城宽带，或某些地区的移动大内网宽带，导致 DNS 延迟很高或无法解析到距离较近的 CDN；否则没有必要使用 DNS 优化插件。**

该功能位于「网络」→「DHCP/DNS」页面中，**务必关闭**。

> [!CAUTION]
> 若不关闭，有可能会引起 DNS 解析问题，并会导致本方案的广告拦截设置无法拦截部分非直连域名。

某些固件中可能没有这个选项，忽略该步骤即可。

### 1.3 确保 OpenWrt 可以正常访问 GitHub 或加速 CDN

> OpenClash 的数据库、插件和内核更新均需要访问 GitHub 或 jsDelivr CDN。

无论当前网络能否稳定访问 GitHub，都建议提前在 OpenClash 中启用 GitHub 地址修改功能。

1. 进入「OpenClash」→「覆写设置」→「常规设置」。
2. 在「GitHub 地址修改」下拉菜单中选择一条 CDN 线路。
3. 推荐选择 **testingcf**。该 CDN 是 jsDelivr 的 Cloudflare 线路，也可以根据实际网络情况尝试其他选项。
4. 点击页面下方的「应用配置」，使设置生效。

## 2. ⚙️ 设置 OpenClash 常规设置

以下列出 OpenClash 的设置内容。每个需要调整的页面均有图文说明，请按照顺序逐页设置。

所有未提及的页面，均不需要设置。

### 2.1 模式设置

> [!WARNING]
> **注意：本方案适用于 `Fake-IP` 模式。如果不使用 Fake-IP 模式，本方案不适用。**

首先在页面下方切换到 Fake-IP 模式，然后在上方的运行模式中选择「Fake-IP（增强）」。

如果页面中没有「使用 Meta 内核」选项，属于正常现象，因为目前 OpenClash 仅提供 Meta 内核。

> [!TIP]
> 「Fake-IP（增强）」模式通常具有较低的性能开销。如果出现 NAT 问题，可以尝试切换到「Fake-IP（混合）」模式，并**启用** UDP 转发。
> 如果固件包含 Docker 功能，可以直接选择「Fake-IP（TUN）」模式。
> 如果非直连游戏网络存在特殊需求，请分别测试各模式下的 NAT 状态。

### 3.2 DNS 设置

首先启用「自定义上游 DNS 服务器」，然后根据实际环境选择以下一种设置：

<a id="情况一主路由拨号--使用运营商-dns-推荐"></a>

#### 情况一：主路由拨号并使用运营商 DNS（推荐）

1. **启用**「追加上游 DNS」。
2. **禁用**下方「NameServer」组中的所有服务器。
3. **禁用**下方「Fallback」组中的所有服务器。

「追加上游 DNS」会将 WAN 接口取得的 IPv4 DNS、IPv6 DNS 和 PPPoE 网关追加为上游 DNS 服务器，无需手动配置。

这是维护者在相应前提下的推荐设置，但部分地区运营商 DNS 可能偶发异常；如遇直连访问不顺畅，可尝试切换到下面的设置，改用加密 DoH 服务器替代运营商 DNS。

> *2025 年 7 月 22 日更新：部分地区用户反馈运营商服务器偶发异常；可以切换到加密 DoH 服务器，以排除运营商侧影响。*

<a id="情况二使用加密公共-dns-服务器或-smartdns-之类的-dns-插件不区分主路由旁路由"></a>

#### 情况二：使用加密公共 DNS 服务器或 SmartDNS 等 DNS 插件（主路由和旁路由均适用）

1. **禁用**「追加上游 DNS」。
2. **使用第三方服务器：** 在「NameServer」中启用阿里和 DNSPod 的 DoH 服务器（地址中包含 `https`），并确保「Default-Nameserver」中至少启用一个服务器。
3. **使用 SmartDNS：** 启用「NameServer」组中的第一个服务器，并将地址修改为 SmartDNS 的地址和端口，例如 `127.0.0.1:6053`。
4. **禁用**「Fallback」组下的所有服务器。

在 SmartDNS 设置中，务必关闭 DNS 劫持，只保留第一服务器组，并仅添加所在国家或地区的 DNS，用于解析直连域名。

在多入口或复杂网络环境中，如果启用了 SmartDNS，建议在「NameServer」中额外启用一个 DoH 服务器，并在该服务器的设置中启用「节点域名解析」、禁用「直连域名解析」，以避免 OpenClash 使用 SmartDNS 解析节点域名。

> [!IMPORTANT]
> 「追加上游 DNS」和下方的「NameServer」通常**二选一**即可；存在明确需求时也可以叠加使用。OpenWrt 作为主路由时，建议按照图示设置。
>
> 「追加上游 DNS」的作用是将 WAN 接口取得的运营商 IPv4 DNS、IPv6 DNS 和 PPPoE 网关自动设置为上游 DNS 服务器。

其余选项可以参考图示设置。

旁路由用户请参考上述第二种设置，并根据实际需要选择 DNS 服务器。

<img width="1187" alt="7" src="https://github.com/user-attachments/assets/526800ab-d167-41b0-a3ab-997b930ebbba" />

在本方案中，「NameServer」仅负责以下域名的 DNS 解析：

1. 直连类域名（不经内核）。
2. 经内核处理但最终直连的域名。

因此，没有必要在「NameServer」中填写多个服务器，也不要填写其他国家或地区的公共 DNS 服务器。
如果不使用运营商 DNS，可以选择 AliDNS、DNSPod 等第三方 DoH 或 DoT 服务器。部分 DoH 服务器支持 HTTP/3 和 QUIC，启用后可以显著降低解析请求的时间开销。

> [!IMPORTANT]
> **为什么要取消「Fallback」服务器？**
>
> 在 Fake-IP 模式下，如果取消了「Fallback」服务器，OpenClash 会把解析请求交由远端完成。
> 让解析与实际出站链路保持一致，通常更容易获得可用且一致的解析结果。

如果出站侧解析不可用（较少见），可以启用「Fallback」服务器作为备用，并选择任意可用的 DoH 服务器；同时建议在本页启用「遵循规则」。

如果使用域名形式的 DoH 服务器，例如 `https://dns.alidns.com/dns-query`，则需要启用「Default-Nameserver」服务器。

## 4. 📝 添加订阅和规则配置

完成前文的 OpenClash 插件设置后，接下来需要为 OpenClash 提供**节点来源、策略组和分流规则**。

本项目为同一套分流逻辑提供了三种实现路径：

1. **订阅转换与 `.ini` 模板**。
2. **覆写模块远程调用 YAML 配置**。
3. **下载 YAML，手动填写订阅后上传**。

三种路径解决的是同一个问题，只是配置生成、更新和维护方式不同。无论选择哪一种，OpenClash 最终都会在启动前，根据前文完成的 LuCI 页面设置，对配置文件进行覆写并生成实际交给 Mihomo 内核运行的配置。

> [!IMPORTANT]
> **以下三种方式只需要三选一。**
>
> 不要同时使用订阅转换、远程 YAML 覆写模块和手动 YAML 来维护同一套配置。多种路径叠加后，可能出现配置文件被反复切换、同名文件被覆盖、订阅来源不明确、故障时无法判断配置究竟来自哪里等问题。

<!-- -->

> [!NOTE]
> 本项目提供的模板与 YAML，均由维护者依据常见使用场景和实际经验设计，不可能预知每位用户的节点命名、地区、业务和网络环境。需要完全贴合个人需求时，应在理解现有配置后自行修改或编写 YAML。

### 4.1 三种配置方式的区别与选择

三种方式使用的**规则顺序、策略组结构和分流目标尽量保持对齐**。例如，选择 `Custom_Clash` 标准版时，无论通过 `.ini` 订阅转换、远程 YAML 覆写模块，还是手动上传 `Custom_Clash.yaml`，得到的核心分流逻辑均应当一致。

它们的主要差异不在「分流效果」，而在于配置由谁生成、订阅由谁读取和解析、后续参数是否便于调整、能否自动跟随仓库更新，以及用户对最终 YAML 的控制程度。

| 使用方式 | 实现方式 | 主要优点 | 代价与限制 | 推荐人群 |
| :-- | :-- | :-- | :-- | :-- |
| **① 订阅转换与模板** | OpenClash 保存订阅与转换参数，并向订阅转换后端发起转换请求；由后端套用 `.ini` 转换模板组合订阅链接并生成完整 YAML | 日常使用最方便；可直接在既有订阅编辑界面切换模板、开关 UDP 或跳过证书验证、设置节点包含或排除关键词等，无需编辑 YAML；适合大多数用户 | 订阅链接会提交给所选后端；依赖后端可用性及其与模板的兼容性；公共后端存在隐私和稳定性边界 | 希望通过 OpenClash 页面管理订阅，并经常调整转换参数的用户 |
| **② 覆写模块远程调用 YAML** | OpenClash 下载本项目 `.conf` 模块；模块再下载对应 YAML，并把环境变量中的订阅写入 YAML | 不经过订阅转换；无需手动编辑 YAML；可自动跟随仓库配置更新 | 规则版本和可调参数主要由远程 YAML 与模块决定；切换版本需要更换模块或修改 `EN_KEY2`，不如订阅转换灵活 | 不希望使用转换后端，又不想手动维护 YAML 的用户 |
| **③ 下载 YAML，手动修改并上传** | 用户下载本项目 YAML，在本地填写订阅或自建节点，再上传到 OpenClash | 控制力最高；配置内容可审计、可固定、可深度修改；不依赖转换后端和远程模块 | 每次调整都需要编辑或重新上传 YAML；仓库后续更新不会自动合并；需要具备基本 YAML 和 Mihomo 配置知识 | 需要固定版本、深度个性化或维护静态自建节点的进阶用户 |

OpenClash 在订阅转换路径中承担的是**参数管理、请求发起、结果下载和配置调度**，并不自行读取或解析订阅内容。节点协议识别、节点合并、关键词过滤和模板生成等工作均由后端完成。

#### 快速选择

| 使用需求 | 建议选择 |
| :-- | :-- |
| 第一次使用，不想研究配置文件 | **订阅转换与 `Custom_Clash`** |
| 希望节点故障后自动切换，不想手动选择节点 | **订阅转换与 `Custom_Clash_Fallback`**，或对应 YAML 路径 |
| 经常切换标准、Lite、GFW、Full 或对应的故障转移模板 | **订阅转换**，直接编辑既有订阅并切换模板 |
| 经常调整 UDP、跳过证书验证或节点关键词筛选 | **订阅转换** |
| 不希望把订阅提交给 SubConverter-Extended 后端 | **远程 YAML 覆写模块** |
| 希望配置自动跟随本项目更新，但不想编辑 YAML | **远程 YAML 覆写模块** |
| 已确定采用覆写模块，并需要在 8 个常规版本间切换 | **`Custom_Clash_8in1.conf` 覆写模块** |
| 希望配置长期固定，不受远程文件变化影响 | **下载 YAML，手动修改并上传** |
| 自建节点以可通过 HTTP 获取的 Provider 或订阅形式提供，并以订阅节点作为后备 | **自建节点 Provider 覆写模块** |
| 自建节点需要直接填写 VLESS、Hysteria2、TUIC 等协议参数 | **手动修改 `Custom_Clash_Selfhosted_Manual_Fallback.yaml`** |
| 需要完全自定义配置文件参数 | **下载 YAML，手动修改并上传** |

### 4.2 本项目提供的分流逻辑与文件对应关系

#### 文件名规律

本项目正式配置文件遵循统一命名规则：

```text
Custom_Clash[_Lite|_GFW|_Full][_Fallback].扩展名
```

命名中的 `Custom_Clash` 表示标准版，`_Lite`、`_GFW`、`_Full` 分别表示轻量版、极简 GFW 版和重度分流版；追加 `_Fallback` 表示主要代理型策略组采用故障转移逻辑。扩展名 `.ini`、`.yaml`、`.conf` 分别对应订阅转换模板、OpenClash 或 Mihomo 可加载的最小 YAML，以及 OpenClash 覆写模块。

例如：

```text
Custom_Clash_Lite_Fallback.ini
```

表示「轻量故障转移版」订阅转换模板。

```text
Custom_Clash_Lite_Fallback.yaml
```

表示与之对应、可以直接加载的 YAML 配置。

```text
Custom_Clash_Lite_Fallback.conf
```

表示用于远程下载并写入该 YAML 的 OpenClash 覆写模块。

#### 8 套常规分流逻辑

本项目提供 4 种规则规模，每种又分为普通版与故障转移版，共计 8 套常规逻辑。

| 分流逻辑 | 文件名（不含扩展名） | 主要特点 | 建议 |
| :-- | :-- | :-- | :-- |
| 标准版 | `Custom_Clash` | 常用业务分流、地区组和性能开销之间较为均衡 | 大多数用户优先选择 |
| 标准版 故障转移 | `Custom_Clash_Fallback` | 标准版规则不变，主要代理组改为按候选顺序自动故障转移 | 希望减少手动切换的用户 |
| 轻量版 | `Custom_Clash_Lite` | 减少独立业务策略组，保留基础代理、直连和常用服务分流 | 低性能设备或偏好简洁的用户 |
| 轻量版 故障转移 | `Custom_Clash_Lite_Fallback` | 轻量规则结构与自动故障转移 | 希望轻量且无人值守的用户 |
| 极简版 | `Custom_Clash_GFW` | 主要匹配 GFW 域名及 Telegram、Facebook、Twitter 等相关 IP，其余流量默认直连 | 只需要最基础代理逻辑的用户 |
| 极简版 故障转移 | `Custom_Clash_GFW_Fallback` | 极简规则与自动故障转移 | 极简需求且不想手动切换的用户 |
| 重度分流版 | `Custom_Clash_Full` | 在标准版基础上增加更多业务、国家、地区和节点用途分类 | 节点丰富、需要精确选路的进阶用户 |
| 重度分流版 故障转移 | `Custom_Clash_Full_Fallback` | 重度分流结构与自动故障转移 | 需要复杂分流又希望自动切换的用户 |

> [!TIP]
> 看不懂上表时，优先选择：
>
> - 希望手动切换出口：`Custom_Clash`。
>
> - 希望自动故障转移：`Custom_Clash_Fallback`。

四种规则规模可以概括为：标准版覆盖常用业务和六个主要地区组；Lite 版删减细分流媒体与业务组，只保留基础分流；GFW 版只处理 GFW 及相关 IP，未命中流量默认直连；Full 版则在标准版上继续增加 Talkatone、OneDrive、Copilot、PT、PayPal，以及更多国家、地区、家宽和低倍率节点分类。

#### 普通版与故障转移版

普通版的主要业务策略组使用 `select`，用户可以在控制面板中手动选择地区组、自动选择组或具体节点，适合需要明确控制流媒体地区、AI 服务地区或特定出口的场景。故障转移版的主要代理型策略组使用 `fallback`，会按候选顺序进行健康检查，并在当前候选不可用时自动切换，更适合无人值守。

> [!WARNING]
> `fallback` 只根据健康检查地址判断候选是否可连接，**不能判断节点是否具备 Netflix、ChatGPT、Disney+ 等服务的地区解锁能力**。
>
> 本节所说的故障转移版使用 `fallback` 策略组类型，与 DNS 设置中的「Fallback」服务器没有关系。

#### YAML 额外提供的 2 套自建节点逻辑

除上述 8 套常规逻辑外，`cfg/yaml` 目录还提供 2 套「自建节点优先、订阅节点后备」的配置。

| YAML 文件 | 自建节点来源 | 分流逻辑 | 适用场景 |
| :-- | :-- | :-- | :-- |
| `Custom_Clash_Selfhosted_Manual_Fallback.yaml` | 在 YAML 顶层 `proxies` 中直接填写静态节点参数 | 基于标准故障转移版扩展；自建节点组优先，订阅节点地区组后备 | 需要直接维护 VLESS、Hysteria2、TUIC 等协议参数的用户 |
| `Custom_Clash_Selfhosted_Provider_Fallback.yaml` | 通过独立的 `selfhost` HTTP Proxy Provider 加载 | 基于标准故障转移版扩展；`selfhost` 优先，`provider1` 节点订阅后备 | 已有自建节点订阅、Provider YAML 或可通过 HTTP 获取的节点列表 |

两者都以自建节点作为首选出口、订阅节点作为后备。区别在于 Manual 版把节点参数直接写进 YAML，Provider 版只保存一个可通过 HTTP 获取的自建节点订阅地址。

> [!CAUTION]
> `Custom_Clash_Selfhosted_Manual_Fallback.yaml` 中自带的节点仅为格式示例，服务器地址、端口、UUID、SNI、Reality 公钥、Short ID 等均为占位内容。未替换时节点不可用。

#### 10 个 YAML 与 10 个覆写模块的对应关系

`cfg/yaml` 目录中有 10 个正式 YAML：

```text
8 个常规 YAML
+ 1 个手动维护的自建节点 YAML
+ 1 个自建节点 Provider YAML
= 10 个 YAML
```

`overwrite/yaml` 目录中也有 10 个覆写模块：

```text
8 个常规 YAML 的单独模块
+ 1 个 8 合 1模块
+ 1 个自建节点 Provider 模块
= 10 个模块
```

两者数量相同，但存在一个关键差异：

| 项目 | 是否有对应关系 | 原因 |
| :-- | :-- | :-- |
| 8 个常规 YAML | 各有 1 个同名单独模块 | 可以用统一的 `EN_KEY1` 写入 `provider1.url` |
| `Custom_Clash_Selfhosted_Provider_Fallback.yaml` | 有对应模块 | 可以分别用 `EN_KEY1` 和 `EN_KEY2` 写入节点订阅与自建 Provider URL |
| `Custom_Clash_Selfhosted_Manual_Fallback.yaml` | **没有通用模块** | 静态节点协议和字段差异太大，不能用少量通用环境变量安全映射 |
| `Custom_Clash_8in1.conf` | **没有同名 YAML** | 它是 8 个常规 YAML 的统一选择器，通过 `EN_KEY2` 决定下载哪一个 YAML |

> [!IMPORTANT]
> 因此，不要根据「文件数量都是 10 个」误以为它们完全一一对应。

#### 完整 YAML 示例不属于正式配置

`cfg/yaml/Complete_YAML_Configuration_Template.yaml` 用于展示 Mihomo 完整配置结构，包括端口、DNS、TUN、嗅探、GeoData 等参数。

该文件是学习和对照用模板，**不计入上述 10 个正式 YAML，也不建议直接作为本方案配置导入**。本项目正式 YAML 只保留节点来源、策略组、Rule Provider 和规则，其他运行参数交由 OpenClash LuCI 管理。

### 4.3 使用订阅转换与模板

#### 4.3.1 实现流程与技术原理

本项目的 8 个 `.ini` 模板均使用 **订阅转换** 后端完成订阅转换。OpenClash 本身不读取、不解析订阅链接，也不负责识别其中的节点协议；它只保存用户填写的订阅与转换参数，组合转换请求，并下载后端返回的 YAML。

完整流程如下（以本项目配套的 SubConverter-Extended 后端为例）：

```text
用户在 OpenClash 中保存订阅与转换参数
    ↓
OpenClash 向后端发起转换请求
    ↓
后端读取所选 .ini 模板
    ↓
生成包含订阅、策略组和规则的 YAML
    ↓
OpenClash 下载生成结果
    ↓
OpenClash 根据 LuCI 设置再次覆写
    ↓
生成实际交给 Mihomo 内核的运行配置
```

`.ini` 文件本身不是 Mihomo 可以直接运行的配置。它描述的是后端应当生成哪些规则、策略组和节点分类，必须经过后端转换为 YAML。

订阅转换的主要优势不仅是首次添加简单，更在于后续维护方便。配置建立后，可以直接在 OpenClash 现有的订阅编辑界面修改模板、UDP、跳过证书验证、节点包含或排除关键词、自定义参数及更新时间，保存后重新更新即可生效。与覆写模块相比，它提供更多面向单个订阅的可调参数；与手动上传 YAML 相比，它不需要反复下载、编辑和上传文件。

模板套用、分流规则生成均由后端处理，因此订阅链接会提交给所选后端，最终结果也依赖后端的可用性。

> [!WARNING]
> 订阅链接通常包含访问凭据。使用公共后端时，必须理解订阅地址会被提交给该后端。
>
> 对隐私和可靠性要求较高的用户，应自行部署后端，或改用本章 4.4、4.5 的 YAML 路径。

#### 4.3.2 本项目订阅转换模板的区别

| 模板 | 分流规模 | 主要策略组类型 | 适用场景 |
| :-- | :-- | :-- | :-- |
| `Custom_Clash.ini` | 标准 | `select` | **默认推荐**；常见业务覆盖完整，仍可手动选择出口 |
| `Custom_Clash_Fallback.ini` | 标准 | `fallback` | **默认推荐的自动切换版本**；适合无人值守 |
| `Custom_Clash_Lite.ini` | 轻量 | `select` | 不需要复杂流媒体和业务分组，重视简洁 |
| `Custom_Clash_Lite_Fallback.ini` | 轻量 | `fallback` | 轻量配置并希望自动切换 |
| `Custom_Clash_GFW.ini` | 极简 | `select` | 只代理 GFW 相关流量，其余默认直连 |
| `Custom_Clash_GFW_Fallback.ini` | 极简 | `fallback` | 极简分流并希望自动切换 |
| `Custom_Clash_Full.ini` | 重度 | `select` | 节点丰富，需要更多业务、地区和节点用途分类 |
| `Custom_Clash_Full_Fallback.ini` | 重度 | `fallback` | 重度分流并希望所有主要业务组自动故障转移 |

> [!TIP]
> 不确定如何选择时：
>
> - 需要自己在面板中决定出口：选择 `Custom_Clash.ini`；
>
> - 希望节点不可用时自动切换：选择 `Custom_Clash_Fallback.ini`。

### 4.4 使用覆写模块远程调用 YAML

#### 4.4.1 实现流程与技术原理

本项目的 YAML 覆写模块不是「在现有配置末尾追加几条规则」，而是一套**下载、写入并切换完整最小 YAML** 的自动化流程。

执行过程如下：

<details>
<summary>查看覆写模块生成配置流程</summary>

```text
远程覆写模块被下载并保存到
/etc/openclash/overwrite/<模块名>
    ↓
OpenClash 启动时读取已启用且匹配当前配置的覆写模块
    ↓
读取模块参数，并将 EN_KEY 导出为环境变量
    ↓
DOWNLOAD_FILE 下载对应 YAML 至
/etc/openclash/config/<配置名>.yaml
    ↓
CONFIG_FILE 临时指定本次启动使用的配置路径
    ↓
SUB_INFO_URL 关联订阅信息查询地址
    ↓
OpenClash 复制原始 YAML 至临时目录
/tmp/<配置名>.yaml
    ↓
yml_change.sh 根据 LuCI 设置修改配置
    ↓
yml_rules_change.sh 处理规则、策略组等内容
    ↓
执行覆写模块的 [Overwrite] / [YAML] 阶段
    ↓
ruby_map_edit 写入 proxy-providers.*.url
    ↓
规范化 provider 本地缓存路径
    ↓
生成最终运行配置
/etc/openclash/<配置名>.yaml
    ↓
Mihomo 加载运行配置
```

### 4.5 下载 YAML，手动填写订阅后上传

#### 4.5.1 实现流程与技术原理

手动 YAML 路径的流程如下：

```text
从 GitHub 下载本项目 YAML
    ↓
上传到 OpenClash 配置管理
    ↓
编辑 proxy-providers 或 proxies 并保存
    ↓
OpenClash 根据 LuCI 设置覆写
    ↓
Mihomo 直接拉取 Provider 并运行
```

本项目的正式 YAML 是 OpenClash 专用的**最小配置**，主要保留 `proxy-providers`、`proxy-groups`、`rule-providers` 和 `rules`；只有自建 Manual 版额外使用顶层 `proxies` 保存静态节点。

端口、运行模式、DNS、IPv6、TUN、嗅探、GeoData、日志和控制器等参数由 OpenClash LuCI 根据前文章节的设置写入，不需要在本项目最小 YAML 中重复维护。

该方式不经过订阅转换，也不需要远程覆写模块。Mihomo 或 OpenClash 会直接从 YAML 中的 `proxy-providers` 地址拉取节点。与订阅转换相比，YAML 的控制范围更完整，但切换分流版本、修改节点过滤方式或调整 Provider 时都需要重新编辑并上传文件，日常维护不如直接编辑订阅参数方便。

> [!NOTE]
> 手动上传的 YAML 不会自动合并本项目后续更新。需要升级时，应备份当前可用配置，再对比新旧文件迁移 Provider、策略组和规则变化。

##### 填写普通 YAML 的订阅链接

在 YAML 中找到：

```yaml
proxy-providers:
  provider1:
    type: http
    url: "url"  # 填入订阅链接
```

将：

```yaml
url: "url"
```

替换为实际使用的第三方服务订阅链接：

```yaml
url: "https://example.com/your-subscription"
```

保留双引号，其他内容不需要修改。

> [!CAUTION]
> 只替换 `provider1` 下的占位订阅地址，不要使用全文替换把规则下载地址、健康检查地址等其他 URL 一并改掉。

##### 多个节点订阅的处理方法

需要多个 Provider 时，可以复制 `provider1`，依次命名为 `provider2`、`provider3`：

```yaml
proxy-providers:
  provider1:
    type: http
    url: "https://example.com/sub1"
    interval: 3600
    path: ./proxy_provider/provider1.yaml
    proxy: DIRECT

  provider2:
    type: http
    url: "https://example.com/sub2"
    interval: 3600
    path: ./proxy_provider/provider2.yaml
    proxy: DIRECT
```

同时还必须：

1. 为每个 Provider 设置不同的名称；
2. 为每个 Provider 设置不同的 `path`；
3. 将新增 Provider 加入需要使用它的策略组 `use` 列表。

例如：

```yaml
use:
  - provider1
  - provider2
```

只复制 Provider 而不加入策略组 `use`，新 Provider 的节点不会出现在相关策略组中。

##### 填写自建节点配置

###### Manual 版

`Custom_Clash_Selfhosted_Manual_Fallback.yaml` 中需要同时处理两部分：

1. 在 `provider1.url` 填写节点订阅。
2. 在顶层 `proxies` 中替换自建节点示例。

示例中的以下字段必须按服务端实际配置修改：

```text
server
port
uuid
servername
public-key
short-id
```

使用其他协议时，可以删除整个 VLESS 示例节点，再按照 Mihomo 官方格式填写 Hysteria2、TUIC、SS、Trojan 等节点。

###### Provider 版

`Custom_Clash_Selfhosted_Provider_Fallback.yaml` 中需要填写：

```yaml
proxy-providers:
  provider1:
    url: "节点订阅地址"

  selfhost:
    url: "自建节点 HTTP Provider 或订阅地址"
```

`selfhost.url` 不能直接填写单条节点 URI，必须是可通过 HTTP 或 HTTPS 获取的订阅或 Provider 文件。

> [!IMPORTANT]
> 手动 YAML 方式的最大优点是配置完全由用户控制，代价是也需要由用户自行维护。本项目更新 YAML 后，本地文件不会自动获得新规则、策略组或修复，需要自行对比并迁移变更。

## 6. 🏆 检验结果

请按照以下步骤检查本方案的设置效果。

> [!CAUTION]
> Clash 面板中的「漏网之鱼」策略组不要选择直连，否则将无法通过 DNS 泄漏检测网站的测试。

### 6.1 检查 DNS 是否存在泄漏

访问 [IPLEAK.NET](https://ipleak.net/) 检查是否存在 DNS 泄漏。

正常情况下，页面上方应显示当前出站的 IPv4 和 IPv6 地址（或仅 IPv4）；页面下方不应显示本地网络或运营商 DNS 服务器条目。

<img width="1495" alt="ipleak" src="https://github.com/user-attachments/assets/ec4b8999-3195-4a5e-a5bd-c51ab4fbbd37" />

DNS 泄漏检测请以 [IPLEAK.NET](https://ipleak.net/) 和 [BrowserLeaks DNS](https://browserleaks.com/dns) 的结果为准。

某些 DNS 泄漏检测网站，例如 [BrowserScan DNS Leak Test](https://www.browserscan.net/zh/dns-leak)，其检测服务器使用部分 DDNS 服务商的域名。为避免影响 DDNS 服务，本项目规则会强制直连 DDNS 类域名，并使用本地解析器处理。因此，这类检测网站可能显示「泄漏」，属于正常现象，可以忽略。

### 6.2 检查 IPv6 分流情况

仅限第三方远端服务支持 IPv6 出站的情况。

> [!IMPORTANT]
> 建议优先使用 Edge、Chrome 或其他 Chromium 内核浏览器进行 IPv6 测试，并提前关闭浏览器的安全 DNS 功能。
>
> Firefox 默认支持 IPv6，也可以用于测试。如果此前在 `about:config` 中手动禁用了 IPv6，请先恢复默认设置。

访问 IPv6 测试网站：[https://ipv6-test.com/](https://ipv6-test.com/)

网页中的「Address」项目应显示当前第三方远端服务出站的 IPv4 和 IPv6 地址。两个地址均显示时，表明 IPv4 和 IPv6 出站都在正常工作。

<img width="1178" alt="test66" src="https://github.com/user-attachments/assets/543c1ad9-f43c-4803-bd40-aa8f827f710a" />

分别访问 test-ipv6 测试网站的镜像站点和原站点：

#### 1. 本地站点测试

镜像站点：[https://testipv6.cn/](https://testipv6.cn/)

访问镜像站点时，检测页面应显示宽带的 IPv4 和 IPv6 地址，以及本地运营商名称（如 CHINA UNICOM），并以 10/10 的评分通过测试。

<img width="939" alt="ipv61" src="https://github.com/user-attachments/assets/aed346b9-0a5a-49b0-b5a0-f597fd1d0d6d" />

#### 2. 远端站点测试

原站点：[http://test-ipv6.com/](http://test-ipv6.com/)

启用 OpenClash 后，访问远端站点时，检测页面应显示当前第三方远端服务出站的 IPv4 和 IPv6 地址，以及对应的网络运营商信息，并以 10/10 的评分通过测试。

<img width="930" alt="ipv62" src="https://github.com/user-attachments/assets/5eadf958-c947-486c-b3b6-e07c49bae790" />

如果以上两个网站测试均通过，说明 IPv6 分流已达到本方案的预期结果。
